# 离线取包：把一个线上游戏变成可复现的夹具

面向的读者：想让工具在自己游戏上出"位级复现"结论的作者，以及想知道
"复现等级"这四个字到底意味着什么的评委。

## 1. 问题：远端应用的复现等级天生低一档

`playtest` 的时间与随机性上限来自两处劫持：`requestAnimationFrame`/定时器进虚拟时钟，
`Math.random` 进种子。这两处覆盖了游戏循环本身，但覆盖不到**响应什么时候到**。

一个真实应用在加载时会拉模块、图片、字体；这些字节的到达顺序决定
"哪一帧里 DOM 是什么样"。于是同一份 (seed, 动作序列) 在远端跑两次，
逐帧哈希会在某一分歧 —— 我们把它如实标成 `async_dependent`，
而不是假装它是 `bit_reproducible`。只要非确定源还在网络那一层，逐帧全等就无从保证。

⚠️ 但别把这句话当天花板用。实测：真实第三方作品上曾经停在 `async_dependent` 的包，
在**取包离线之后**并没有立刻变绿——原因是回放路径和录制路径不一致（第 6 节）。
对齐之后曾取得单次 `replayed=true`（23/23）；🔴 但后来在同一份输入 HAR 上各重放三遍，
23 步那枚第一遍在第 18 步分叉 ⇒ 它现在记 `async_dependent`（🔴 11-08 撤回后台账剩 3 枚：
2 枚 `bit_reproducible` ＋ 1 枚 `async_dependent`，现读 `evidence/corpus.json` 与 §5.5）。
26 步那枚属 11-05 旧快照，20/26 → 20/26 → 21/26
**分歧点自己会移动**，跨快照包身份不同，只作历史。
"复现不出来"先怀疑仪器，再宣称原理。

## 2. 处置：`capture` 把整站响应录成一个 `.har`

```bash
playtest capture https://someone.ms.show/ --har out/someone.har --warm-clicks
playtest scan    https://someone.ms.show/ --har out/someone.har --seeds 20261105
playtest replay  out/scan/curiosity-20261105-xxxx.json --har out/someone.har   # 退出码 0/1，可进 CI
```

为什么用 `.har` 而不是"下载到一个目录再起本地服务器"：
后者会换 origin。origin 一变，`localStorage` 的键、任何依赖 `location.origin` 的逻辑
就不是同一个应用了。用 HAR 重放时页面仍然认为自己跑在原来那个域名上，
**一行代码、一个 URL 都不用改**。

录制时故意**不注入探针脚本**：镜像应当是"真人打开这个页面所加载的那份内容"。

## 3. 严格离线，且未命中不回源

命中分三档，分别计数（可信度不一样，所以不合并成一个"命中率"）：

| 档 | 含义 | 什么时候用 |
|---|---|---|
| `exact` | URL 逐字相等 | 绝大多数资源 |
| `normalized` | 剥掉易变查询参数（`t=`、`__theme=`、`nonce=`…）后相等 | 平台给 iframe 每次塞一个新时间戳的形态 |
| `root_doc` | 裸根导航命中"该 origin 自己的那份 HTML 文档" | 应用入口被 302 重定向进平台壳的形态 |

未命中**绝不偷偷回源**（回源等于把非确定源请回来），而是当场断掉并计入 `misses`。
两条归一化 URL 撞车时，那一档直接拒绝服务，不"随便挑一条"——
那等于凭空造出一个没人跑过的页面。

## 4. 覆盖面靠"补包"撑开，不靠许愿

`.har` 只覆盖**录制时真的被请求过**的资源。首屏录出来的包，探索一走到第二、三层界面
就会未命中——而且缺的往往是**懒加载的代码分块**，那意味着应用根本到不了那个界面，
读数直接作废，不是"结果不够好"而是"没测到"。

```bash
playtest capture https://someone.ms.show/ --har someone.har --top-up
```

`--top-up` 把旧包当**只读缓存**：已知字节仍从磁盘给（快，且不重复消耗线上），
未命中的放行去线上取并顺便录制，最后按 `(method, url)` 去重合并回同一个 `.har`。
实测一轮：`180 → 206` 条 GET，新取回 22 个 JS + 13 个 CSS + 39 张美术。

诚实的余量：补包的热身目前是"按顺序点前几个按钮"，
它到不了策略能走到的地方，所以**深层路径仍然会未命中**，需要多补几轮
（或在录制中的 context 里直接跑 episode，这一步还没做）。

## 5. 镜像兜不住什么（明说）

- **服务端状态**：`POST` 一律算未命中。带推理接口的应用（如"输入一段设定，生成一章小说"）
  离线跑不通，这不是包没做好，是它本来就不是纯客户端游戏。这类应用只做只读探测。
- **装饰类未命中不影响确定性**：两次跑都同样地缺，指纹一致。
  但**代码字节（js/css）未命中**时这一轮读数作废 —— 那已经不是那个游戏了。
  这条判据写在 `tests/m3_offline.py` 里，不是写在文档里。
- **离线摘掉网络，解码这一层以前也摘不掉 —— 11-06 下午修掉了**：图片解码完成时刻不在虚拟时钟的
  帧栅格上，所以"进入新场景"那一步曾跨跑分歧（同一份包三次重放 `20/26 → 20/26 → 21/26`，
  分歧点自己移动；当时如实降格 `async_dependent` 并报出分歧在第几步）。
  🔴 根因不是"解码慢"：被接管的时钟只在我们叫它走的时候走，**"推进 16 帧"消耗的墙钟时间≈0**，
  所以"连续两次读数相同"这个静息条件几乎必然在解码还没落地的那一瞬间成立。
  现在的静息条件是三条同时成立：**两次哈希相同 · 没有在途图片解码 · 资源条目数不再增长**，
  并且只在真有在途工作时才睡一小段真实时间（`settle_poll_ms`，夹具零成本）。
  改后读数（**绑输入快照**，跨快照不可互借）：11-05 那份快照的两枚包各连重放三遍都
  `bit_reproducible`、`mismatch=null`，且同一 seed 连录两遍的动作序列逐值一致
  （仓内等价判据现跑 `PYTHONUTF8=1 python tests/m3_offline.py`）。🔴 11-06 换了一份 HAR 重取后，
  `tools/replay_repeat.py` 把当时台账引用的 6 枚包各重放三遍：**5 枚逐值一致，作品 A（脱敏代号） 23 步那枚
  （`ef6b22c199b40365`）第一遍在第 18 步 `click:button:场景切换按钮` 分叉 ⇒ 如实降格
  `async_dependent`** —— 这条是**未闭合的能力缺口**，不是已经解决。
  🔴 **11-08 再更正**：上面那批三遍读数出自双派发 click 修复**之前**的探针。修好之后，
  其中 3 枚（作品 B（脱敏代号） 5 步 / 作品 C（脱敏代号） 2 步 / 作品 C（脱敏代号） 3 步）在开关控件那一步确定性失配 ⇒ 按纪律从台账移除，
  不记 `async_dependent`（失配是仪器版本绑定，不是游戏的异步）。台账现存 3 枚：
  2 枚 `bit_reproducible` ＋ 1 枚 `async_dependent`（作品 A（脱敏代号） 23 步那枚原级保留 ——
  今天重测虽逐值一致，但**换了输入 ⇒ 今天的绿不许升昨天的级**）。
  逐枚处置见 `evidence/ledger/2026-11-08_ui_dead_end_withdrawal.json`。
  🔴 **归因未闭合，别把"解码漏进指纹"当结论**：三遍的 `wall_ms`（3790 / 3865 / 3604）
  与是否分叉不相关，所以它只是假设之一；另一条更便宜的假设是 `replay()` 的存档注入分支
  （`playtest/trace.py:95` 用"装回存档后哈希变没变"决定要不要 `reboot`，而 `storage_injected`
  这个字段被 `tools/replay_repeat.py` 投影时丢掉了、至今没进 ledger）。
  先做字段级诊断再谈改判据，详见 `README.md` 第 7 条。逐遍读数 `evidence/ledger/*_repeat3.json`，
  校验 `PYTHONUTF8=1 python tools/corpus.py`。
  🔴 **三个身份字段别混读**（ledger 自带 `field_caliber` 块，`tools/corpus.py` 会守它）：
  `pack_id` 是稳定身份（url/seed/动作字符串/defect.signature），**不含** `actions[].hash_after/frame`
  期望时间线 ⇒ 同 `pack_id` ≠ 同字节；`pack_sha256` 是整份包文件的快照哈希（含 `recorded_at` 墙钟），
  每次重生成必漂、且指向 gitignored `out/` 件，**不是可复核绑定**；可复核的输入绑定是
  `offline_har_sha256`（重放实际喂的 HAR 字节，台账 `input_har_sha256` 与它对账）。
  用完预算仍不安息时不假装安静 —— `Snapshot.assets.settle_unsettled` 如实带上。

## 5.5 复现不出来时先查的两条（都是真实踩过的坑）

1. **回放有没有多推一段帧**：装载持久状态之后若无条件再推进一段，
   回放就比录制多走了一段时间；包里那份存档若与干净开机自己会写出来的那份相同，
   什么都不该做（`replay()` 现在用"装上去局面变没变"来判，变了才 `reboot` 让应用在开机时读到）。
2. **回放有没有按包里的帧时间线补齐**：录制时检测器自己也会推进帧
   （`ui_dead_end` 要空推 40 帧确认"真的没反应"）。复现包记了每一步"读到第几帧"，
   回放就要补到那一帧再比 —— 观测的成本也在时间线里，漏掉它，动画/飘字类界面差一帧就对不上。

## 6. 复现等级怎么读

| level | 含义 | 能用来做什么 |
|---|---|---|
| `bit_reproducible` | 同一 (初始状态, 种子, 动作序列) 在新实例里逐帧哈希全等 | 进 CI 当回归闸门；可以断言"修好了/又坏了" |
| `async_dependent` | 缺陷存在过（初始状态一致、前缀可重放），但异步时序不受控 | 可以当"这个问题出现过"的证据；不能当闸门 |
| `unverified` | 连初始状态都对不上 | 不能用，先查探针注入与 frame 解析 |

要拿到 `bit_reproducible`，两条路：游戏侧注册 GSPP adapter 并提供 `snapshot/restore`
（见 `docs/integrate-in-20-lines.md`），或者**不接任何协议**、直接 `capture` 成离线包。
后者对作者零成本，这也是"免费帮本届作品做自动试玩"能成立的原因。
